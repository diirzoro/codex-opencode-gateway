# مراجعة أمن عزل Pi — 11 نوفمبر 2026

**الحالة:** مراجعة مصدر فقط؛ لا يوجد إثبات باختبار حي على TEST.

## النتيجة

- يتحقق المسار HTTP من ملكية المستخدم والمشروع في scope()؛ لكنه لا يفرض عزلاً على أدوات Pi الأصلية.
- يستخدم Pi SDK أدوات bash وread وwrite وedit مع noTools:false، تحت نفس حساب خدمة Node.js.
- cwd الخاص بالمشروع وتوجيهات النظام لا تمنع قراءة مسار مطلق خارج المشروع. ليس في ملف التكامل عزل مستخدم Linux أو حاوية لكل مشروع.
- يوجد PI_AGENT_DIR مشترك. تشغيل الإضافات المشتركة تحت نفس UID يمثل سطح وصول واسع.
- إذا كانت مجلدات مستخدمي TEST تسمح للحساب المشترك بالقراءة، فإن الوصول بين المشاريع محتمل. لا يمكن تأكيد ذلك من المصدر وحده.
- قراءة ملف عام مثل /etc/hostname ليست تسريباً سرياً بذاتها، لكنها تبرز عدم تقييد رؤية نظام الملفات.

## اختبار قراءة أذونات غير مؤذٍ

يوجد السكربت scripts/pi_readonly_isolation_audit.mjs؛ لا يقرأ محتويات الملفات ولا يكتب أو يحذف، وإنما يفحص صلاحيات الملفات عبر stat وaccess فقط. يجب تشغيله تحت نفس UID وmount namespace لخدمة Pi TEST، وبتمرير مساري **مجلدي اختبار** مختلفين:

node scripts/pi_readonly_isolation_audit.mjs /absolute/test-user-a/repo /absolute/test-user-b/repo

- crossProjectReadable=true أو crossProjectWritable=true: فشل عزل صلاحيات نظام التشغيل.
- يظل اختبار أدوات Pi الفعلية مطلوباً، باستخدام ملف تجريبي غير حساس في مجلد عميل اختبار آخر.

**لم يُشغّل هذا الاختبار على VPS بعد، ولذلك لا توجد نتائج حيّة.** لم يغيّر هذا التقرير خدمة Pi أو LIVE أو master أو Workflow.

## تقييم الخطورة

الخطر **مرتفع** عندما تُفعل كل أدوات Pi بما فيها Bash لعدة عملاء تحت نفس UID ومجال ملفات مشترك. فصل المشاريع يتطلب عملية/حاوية أو مستخدم Linux ومنافذ mount معزولة، لا Python chat proxy.
