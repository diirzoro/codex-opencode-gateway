# استكمال عزل أدوات Pi — 18 نوفمبر 2026

الحالة: مرحلة تدقيق وتحضير. لا تغيير في تشغيل LIVE أو الخدمات أو قواعد البيانات أو Workflow. نجاح اختبارات الفحص لا يعني إغلاق ثغرة العزل.

## المرجع والنتيجة

رُوجعت مذكرة Pi_Gateway_Security_Plan_AR بتاريخ 15 نوفمبر، والمصدر master عند ed7f6a2، وخصوصًا integration/pi-central.mjs.

تُنشأ جلسات SDK داخل عملية Node المشتركة، مع noTools:false وتفعيل الأدوات والإضافات والمهارات. يفحص scope() ملكية المسار لطلبات HTTP، لكنه لا ينشئ mount/user namespace للأدوات. cwd ومخزن الاعتمادات المنفصل لكل جلسة لا يشكلان حدودًا لنظام التشغيل. هذه فجوة تصميم مؤكدة من المصدر؛ مدى الوصول الفعلي على VPS يحتاج قياسًا داخل سياق الخدمة.

اختبارات ملكية المعاينة السابقة بحسابين لا تغطي أدوات Pi. اختبارات حاويات المعاينة لا تثبت عزل عملية Pi المشتركة. لا يُدمج PR49 الذي يعطل أدوات البرمجة.

## المرحلة صفر: قياس بلا تعطيل

- [x] مراجعة موضع إنشاء جلسات SDK وحدود التحقق من ملكية المشروع.
- [x] تصحيح أداة فحص الصلاحيات حتى لا تعتبر المسار المفقود أو الفحص خارج سياق الخدمة نجاحًا.
- [x] ثمانية اختبارات محلية للفحص، تشمل المسار المفقود والروابط الرمزية وهوية الخدمة وعدم تعديل الملفات أو إظهار محتواها.
- [ ] مطابقة ملف Pi الذي تشغله الخدمة فعلًا مع SHA المصدر، وإصدار Node/Pi/SDK والموارد المتاحة. لا تطبع البيئة أو المفاتيح أو سطر أوامر قد يحتوي أسرارًا.
- [ ] تحديد PID الفعلي لخدمة Pi والتحقق من UID/GID والمجموعات والقدرات وnamespace وLSM. لا تستنتج الصلاحيات من رد النموذج.
- [ ] تشغيل فحص الصلاحيات تحت سياق التنفيذ نفسه على مجلدين تجريبيين معروفين، لا مجلدات عملاء حقيقيين.
- [ ] قياس زمن أول رد ووقت بدء الأدوات وRSS/CPU للمحادثة الواحدة والمحادثات المتزامنة قبل التغيير.

أمر الفحص المحدّث، بعد الحصول على PID الحقيقي وتشغيله داخل سياق الخدمة:

```sh
node scripts/pi_readonly_isolation_audit.mjs /absolute/fixture-A /absolute/fixture-B --pid PI_SERVICE_PID
```

يجب استبدال الأسماء بمسارات اختبار وPID فعليين. لا تشغله بصلاحية root خارج سياق الخدمة ثم تنسب النتيجة إلى النموذج.

مخرجاته لا تتضمن محتوى الملفات أو المسارات المدخلة أو أسرار البيئة. رمز الخروج 2 يعني أن القياس غير محسوم؛ 1 يعني وجود صلاحيات دليل مشتركة؛ 0 يعني عدم رصد تعرض في صلاحيات الدليل فقط. جميع الحالات تحمل executionIsolationProven:false. اختلاف سياق الصلاحيات أو عدم القدرة على قراءة بياناته الثابتة يجعل النتيجة غير محسومة.

الفحص ليس اختبار قراءة ملف، ولا اختبار أدوات النموذج أو الكتابة أو الشبكة. وجود صلاحية دليل لا يثبت تلقائيًا قراءة كل ملف بداخله؛ وعدمها لا يثبت استحالة الوصول إلى ملف معروف الاسم. تظل اختبارات الأدوات الفعلية إلزامية.

## المرحلة الأولى: حدود تنفيذ المشروع

- [ ] نقل جلسة Pi الأصلية من التنفيذ داخل عملية التحكم إلى عامل Node مستقل لكل مشروع نشط، مع قناة IPC خاصة ومحدودة. هذا فصل تنفيذ داخل التكامل الحالي، وليس محرك AI أو خدمة طابور بديلة.
- [ ] إنشاء namespace ملفات للعملية قبل تحميل SDK أو إضافات المشروع. يُعرض المشروع الحالي فقط للكتابة، وسجل جلسته فقط عند الحاجة. مجلدات بقية المشاريع، إعدادات Gateway، مفاتيح السيرفر، sockets التحكم وDocker وSSH غير مركبة.
- [ ] استخدام جذر تشغيل مصغّر للقراءة فقط، يحوي Node/Pi والمكتبات والبرامج اللازمة. ملفات النظام داخله تكون من بيئة التنفيذ المعزولة، وليست ملفات المضيف. لا يمكن حجب كل ملفات نظام التشغيل حرفيًا مع تشغيل Node/Bash؛ معيار القبول هو منع رؤية ملفات المضيف والعملاء.
- [ ] مستخدم غير مميز، دون sudo أو مجموعة docker أو قدرات إضافية، no-new-privileges، وملف AppArmor/seccomp محدد. لا تستخدم unconfined أو bind لجذر المضيف.
- [ ] /proc خاص بالعامل المعزول، وعدم توريث واصفات ملفات أو بيئة عملية التحكم. تحقق من المجموعات الإضافية والقدرات، لا UID وحده.
- [ ] توفير مساحة مؤقتة محدودة خاصة بالمشروع، مع منع الروابط الرمزية والمسارات المتسابقة من تغيير مصادر الربط عند الإنشاء.
- [ ] لا تعتمد صلاحيات مجلد 0700 لحماية مشاريع تعمل تحت UID واحد؛ ولا تعتمد اعتراض read أو قائمة أوامر Bash كحد أمني.

اختيار وسيلة namespaces أو الحاوية يتوقف على قياس VPS في المرحلة صفر. خدمة حاويات المعاينة الحالية ليست دليلًا على ملاءمتها لتشغيل Pi: المعاينات بلا شبكة، بينما اتصال النموذج يحتاج شبكة مضبوطة. لا تُعاد تسمية حاوية معاينة على أنها عزل Pi دون تنفيذ الضوابط واختبارها.

## المرحلة الثانية: الاعتمادات والشبكة والإضافات

- [ ] تبقى Gateway مسؤولة عن الحسابات والمنح والتهيئة والتجديد، دون Python أو استعلام قاعدة بيانات لكل رسالة أو أداة. يحتفظ Pi بتحقق محلي للمنح.
- [ ] لا تمنح العامل مفاتيح أو سجلات أو اتصالات تخص حسابًا آخر. سر اتصال النموذج الحالي نفسه يجب اعتباره قابلًا للاستخراج من عامل يشغّل كودًا غير موثوق؛ يلزم إبقاؤه خارج عامل الأدوات أو استخدام اعتماد محدود الصلاحية عبر حد اتصال مدقق، قبل وصفه بأنه محمي من Bash.
- [ ] أي قناة اتصال موثوقة مع مزود النموذج تحافظ على Pi SDK وSSE الأصليين، ولا تتحول إلى محرك محادثة أو وكيل Python لكل استدعاء.
- [ ] تحميل إضافات المشروع غير الموثوقة داخل العزل فقط؛ عدم تحميلها في عملية التحكم التي تحمل أسرار جميع العملاء.
- [ ] منع وصول شبكة العامل إلى loopback المضيف والشبكات الداخلية وmetadata وقواعد البيانات وقنوات الإدارة. لا يكفي حجب الملفات إذا بقيت APIs داخلية بلا مصادقة قابلة للاتصال.
- [ ] تحديد سياسة تنزيل تبعيات المشاريع قبل التشغيل؛ لا تفتح شبكة شاملة لتجاوز مشاكل npm/pip. افصل احتياجات البناء عن تشغيل الأدوات والاتصال بالمزود.
- [ ] اختبار إبطال الجلسات عند الخروج أو التعليق أو تغيير ملكية المشروع، وإيقاف المهام التابعة عند الإبطال. لا يكفي إخفاء المشروع من الواجهة.

## المرحلة الرابعة: بوابة القبول قبل التعميم

اختبار بحسابين ومشروعين قابلين للتخلص منهما. ينشئ المشغّل رموزًا عشوائية لا يعرفها النموذج داخل ملفات canary. لا تستخدم أسرار العملاء أو ملفات النظام الحساسة لإثبات الخرق.

| الاختبار | معيار القبول |
|---|---|
| read/write/edit/bash داخل المشروع | تعمل الوظائف الفعلية وتبقى التغييرات في المشروع الصحيح |
| الوصول المباشر لمشروع الحساب الآخر | يفشل داخل أداة Pi نفسها؛ ملف canary الآخر لا يُقرأ ولا يُعدل |
| مسار مطلق أو traversal أو رابط رمزي | لا ينقل الوصول خارج نظام ملفات العامل |
| ملفات canary خاصة بالمضيف | غير مركبة في العامل ولا تُقرأ عبر /proc أو واصفات موروثة |
| الأسرار وقنوات التحكم | لا توجد مفاتيح عملاء آخرين أو sockets المضيف أو بيئة التحكم داخل العامل |
| إضافات ومهارات وكود مشروع غير موثوق | لا تُنفذ خارج العزل ولا توسع الربط أو صلاحيات العامل |
| اتصالات داخلية وmetadata | مرفوضة من داخل العامل نفسه، مع نجاح اتصال النموذج المصرح |
| إلغاء وتعليق وخروج وانتهاء جلسة | إبطال المنحة وإيقاف التنفيذ وإغلاق العمليات التابعة فعليًا |
| التزامن وحدود الموارد | لا يتجاوز العامل الحدود ولا يؤثر اختباره على عميل آخر |
| إعادة تشغيل العامل | استعادة المحادثة والملفات بلا إعادة إنشاء أو فقد بيانات |

يُسجّل دليل التنفيذ الحقيقي وتوقيت الاختبار والنسخة والحدود، دون طباعة الرموز أو الأسرار. ENOENT وحده ورد النموذج وحده وHTTP 404 وحده ليست إثباتًا لعزل الأدوات.

## التفعيل التدريجي والتراجع

1. الاختبار في حساب تجريبي محدد قبل إدخال أي عميل في المسار الجديد؛ لا تغيير شامل لعملية Pi المشتركة قبل إثبات الاستمرارية.
2. تشغيل وضع المقارنة والمراقبة ثم الانتقال للعمال المعزولين حسب القدرة المثبتة. يكون الإعداد مركزيًا ولا يحتاج كل عميل إلى إعداد جديد.
3. لا تغير Workflow أو الدفع أو قاعدة البيانات لتنفيذ هذه المرحلة. عند الحاجة إلى إعادة تشغيل مشتركة، تُحدد الجلسات النشطة ويُوضح الأثر مسبقًا.
4. العودة من فشل العامل المعزول تكون إلى إيقاف المهمة مع حفظ المشروع والجلسة. لا رجوع صامت إلى تنفيذ غير معزول يُعرض للمستخدم على أنه آمن.
5. لا توضع علامة مكتمل للحماية قبل اجتياز الأدوات الفعلية والعزل والاعتمادات والشبكة ودورة الحياة والأداء.
