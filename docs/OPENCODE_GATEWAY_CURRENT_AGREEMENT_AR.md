# OpenCode Gateway — المذكرة التنفيذية الوحيدة (Native-first / Functionality-first)
**تحديث معماري وتوثيقي: 4 نوفمبر 2026** | **مصدر واحد بنفس المحتوى على `updates` و`master`؛ التنفيذ العملي LOCAL فقط، ولا يوجد نشر LIVE** | **المرجع التنفيذي:** [المهمة #47](https://github.com/diirzoro/codex-opencode-gateway/issues/47)

## أحدث تدقيق LOCAL — Python/Native وحدود المطابقة (تقرير DeepSeek، 4 نوفمبر 2026)
- **ما فُحص (وفق تقرير DeepSeek، وليس اختبارًا مستقلًا):** بحث داخل `backend/app` لم يجد تنفيذ inference/chat.completions، ولا `StreamingResponse/EventSource/aiter` لبث SSE من Python، ولا تخزين محادثات أو نماذج في PostgreSQL. هذه **نتائج فحص ساكن محدودة بنطاق البحث**؛ لا تثبت بمفردها سلوك جميع المسارات الحية.
- **التفويض الفعلي:** `native_sessions.py` يصدر `X-Accel-Redirect: @native_session_local` بحسب التقرير، بحيث ينقل Nginx استجابة Native؛ لكن هذا يعني أن طلب الجلسة يدخل Python أولًا لإصدار التفويض. **مطابقة جزئية، لا PASS كامل** لشرط المالك الجديد بأن تكون جميع عمليات Native مباشرة عبر Nginx بلا Python في كل طلب.
- **تحقق النموذج:** `_authorize_native` يستدعي `require_model` لقراءة `/provider` والتحقق من الاتصال وعضوية `model in models` عند كل Prompt. هذا اعتماد Python على حالة Native التشغيلية يخالف الفصل الكامل المطلوب، وإن لم يكن AI inference. المطلوب فصل سياسة الوصول/ملكية المشروع عن دقة النموذج، وترك Model Resolution لـNative، دون فتح منفذ Native أو إزالة عزل المستخدمين.
- **صيانة الفهرس:** `native_catalog_maintenance.py` يشغل `opencode models --refresh` عبر `subprocess` بحسب التقرير (VPS-only). ليس توليد AI، لكنه **تدخل Python في إدارة كتالوج Native**؛ راجعه مقابل سياسة المالك: لا تجعل Python تدير إعدادات/فهرس OpenCode؛ أبقِ أي عملية صيانة أصلية خارج مسار Gateway وموثقة دون تعطيل خدمة مستخدم.
- **القرار التنفيذي التالي:** أولوية عاجلة لإصلاح `401 Invalid session` في LOCAL: فحص `security/sessions.py` و`require_user` وcookies وOrigin وproxy headers وTTL/expiry وlogout/activity، مع Playwright حقيقي على `http://localhost:8080` (تبويبان، refresh، مشروع/محادثة، حالة session منتهية). لا تُعالج الخطأ بإلغاء المصادقة أو إطالة صلاحيتها بلا حد. بعد الإصلاح أعِد قياس المسارات الآمنة ثم صحح انفصال Python/Native المثبت دون خسارة الحماية.
- **الحالة:** تدقيق Python/Native **PARTIAL وليس PASS كاملًا**؛ مشكلة 401 **FAIL قيد المعالجة**؛ تعارض modelID **FAIL**؛ نتائج Playwright التفصيلية والإصلاح المحلي لم تصل بعد. هذا تعديل توثيقي فقط في GitHub؛ لا نشر ولا تغيير للكود المحلي.

## تحديث الاختبارات المحلية — Refresh و401 وNative model (حسب تقرير DeepSeek، 4 نوفمبر 2026)
- **Playwright PASS مبلغ عنه:** تحديث Connections أعاد `connectionsPage` بدل الانتقال إلى Workspace؛ ظهر DeepSeek متصلًا في `providerSelect`؛ إنشاء Native Session نجح. هذه أدلة على الحالات المختبرة فقط ولا تثبت نجاح Refresh في كل الصفحات أو تغيير المشاريع/المحادثات.
- **Native AI FAIL مستمر:** `ProviderModelNotFoundError: Model not found: deepseek/deepseek-v4-pro`؛ لم يصل رد Assistant حقيقي. لا يُثبت التقرير وحده أن فهرس OpenCode 1.19.5 هو سبب الخطأ الوحيد؛ قارِن Native CLI/config/catalog/model resolution وجرّب النموذج مباشرة قبل تعديل Gateway أو مسح أي كاش/إعادة تشغيل.
- **401 — تفسير مرجح حسب التقرير، يحتاج إثبات بالوقت والحالة:** مهلة خمول `IDLE_TIMEOUT=15min`، و`POST /api/auth/activity` يعتمد على أحداث تفاعل حقيقية `isTrusted`؛ حقن JavaScript في بعض الاختبارات لا يولد نشاط مستخدم موثوقًا. مهلة الخمول الطبيعية ليست بحد ذاتها عطلًا. **الخلل الوظيفي المتبقي:** `clearAuthenticatedState` يحذف `og-page` فيضيع موقع المستخدم بعد إعادة الدخول. افصل expiry عن logout الصريح، واحفظ مقصد العودة بصورة مؤقتة وآمنة مرتبطة بالحساب، ولا تعيد فتح صفحة محمية إلا بعد مصادقة وملكية مثبتتين.
- **فصل Native — PARTIAL بالنسبة لقرار المالك النهائي:** افتقاد inference/SSE proxy في Python ووجود `X-Accel-Redirect` يثبت عدم تنفيذ AI من Python، لكنه لا يعني أن كل طلب Native لا يدخل Python؛ `native_sessions.py` يصدر redirect داخليًا بعد التفويض و`require_model` يقرأ `/provider` عند كل Prompt. لا تصنف «مطابق بالكامل» حتى قياس مسار كل طلب وتطبيق فصل آمن لا يتجاوز الملكية أو يعرض مفاتيح مشتركة.
- **ترتيب التنفيذ المحلي:** إثبات نموذج حقيقي من Native أولًا (بدون حذف مفاتيح/جلسات أو تغيير Gateway اعتمادًا على تخمين)، ثم إصلاح حفظ الوجهة بعد انتهاء 401 مع Playwright click/keyboard الحقيقي وليس JS inject وحده، ثم إكمال E2E. أي PASS مبني على تقرير وكيل يحتاج أدلة HTTP/Native والتوقيت.
- **النطاق:** المذكرة توثيق فقط، والتغييرات الوظيفية على LOCAL Windows؛ لا نشر ولا تغيير خدمات خارجية.

## اتفاق المالك النهائي — فصل OpenCode Native تمامًا عن Python (قرار حاكم)
**هذه الفقرة هي المرجع الأعلى عند تعارض صياغات تاريخية أدناه. تحديث توثيقي على GitHub فقط؛ لا يثبت تطبيقها في LOCAL أو TEST أو LIVE.**
1. **Browser → Nginx → OpenCode Native → Nginx → Browser** لجميع أوامر Native: Providers/Models/Variants وAPI Keys/OAuth الأصليين، Agents، إنشاء/قراءة/حذف Sessions، Messages/Prompt/Reply، SSE/Reconnection، Todo، Shell/Read/Write/Edit، Permissions/Questions، History/Abort/Stop، والإعدادات والمرفقات التي يستهلكها المحرك. **لا يدخل Python Gateway في تنفيذ هذه الطلبات أو تحويلها أو التحقق من نموذجها أو بث استجابتها.** لا تقم ببناء Chat/AI Proxy أو registry/queue/DB موازية. لا تُحوّل OpenCode Native إلى OpenCode Web جديد؛ نحتفظ بواجهة Gateway الحالية.
2. **Browser → Nginx → Python Gateway → PostgreSQL** فقط لأعمال الإدارة: Register/Login/Email Verification/Password Recovery، المستخدمون/الأدوار، الفوترة/الخطط، GitHub الإداري، ملكية Projects وWorkspace والبيانات الوصفية للملفات وحصص التخزين. يمكن إصدار سياق وصول/تفويض محدود من إدارة الهوية، لكن **لا استدعاء Python لكل عملية Native**. لا تخزن Python مفاتيح AI أو تاريخ Native.
3. **حماية غير قابلة للتجاوز:** منع وصول مستخدم إلى Native Sessions أو ملفات أو اعتمادات غيره قبل تعميم الوصول على TEST/LIVE. افتح Native عبر Nginx بمسار موثوق غير عام ولا تنقل بيانات الاعتماد إلى المتصفح. صلاحية الوصول تُثبت دون جعل Python وسيطًا للرسائل؛ إن كان OpenCode process-global ولا يحقق العزل بعد، يبقى الإطلاق متعدد المستخدمين BLOCKED إلى أن يوجد فصل موثوق. الوظائف أولًا على loopback المحلي، ولا تعطيل للحماية الأساسية.
4. **Workspace ليس محرك AI:** Gateway تملك معرفات وربطًا إداريًا فقط؛ Native يملك سياق التشغيل الفعلي والتاريخ والجلسات. لا تشغيل Native مستقل لكل Workspace ولا قاعدة رسائل PostgreSQL. بيانات الملفات الإدارية غير ملفات المحادثة التي يستقبلها Native.
5. **Nginx ليس Jenkins:** Nginx للتوجيه، لا لتنفيذ AI. تشغيل LOCAL وفق آخر تقرير: Nginx front `8080`، Gateway `127.0.0.1:8180`، مسارات Native الداخلية `19097/19098`، وOpenCode Desktop `127.0.0.1:61339`؛ القيم من تقرير DeepSeek وتحتاج فحصًا مباشرًا، وهي **ليست** منافذ VPS المذكورة أدناه. وجود منفذين 8080/8180 لتطبيق واحد طبيعي، لكن لا ينبغي استخدام 8180 كباب المستخدم المعتاد. Nginx من مجلد Temp مخاطرة تشغيلية تحتاج فحصًا ومسارًا ثابتًا آمنًا دون إنشاء خدمة ثانية.
6. **مرجعية وثائق واحدة:** فقط `docs/OPENCODE_GATEWAY_CURRENT_AGREEMENT_AR.md` على كل فرع وفي LOCAL؛ لا مذكرات سياسة إضافية. هذا التحديث للوثيقة على `updates` و`master` فقط، دون رفع كود LOCAL أو نشر TEST/LIVE. نسخة LOCAL قد تختلف حتى يزامنها المطور بنفسه.

## مستجد LOCAL — هوية المدير وتشخيص DeepSeek Model (تقرير DeepSeek، 4 نوفمبر 2026)
- **حساب المدير — PASS مُبلغ عنه فقط:** جرى تصحيح `username` و`username_identity` في PostgreSQL المحلي من اسم الاختبار إلى `admin`؛ تقرير DeepSeek ذكر نجاح تسجيل الدخول HTTP 200 بدور admin. **لا تُدرج كلمة المرور أو أي سر في المذكرة**. مراجعة الحسابات التجريبية وتغيير كلمات المرور المعروفة ضرورية قبل إتاحة الوصول للآخرين؛ لا تغير حسابات حقيقية دون إذن.
- **Native inference — FAIL قائم:** سجّل OpenCode Native `ProviderModelNotFoundError` للنموذج `deepseek/deepseek-v4-pro`. عند تمرير `modelID=deepseek-v4-pro` ظهر تشخيص `deepseek/deepseek-v4-pro`، وعند تمرير `modelID=deepseek/deepseek-v4-pro` ظهر `deepseek/deepseek/deepseek-v4-pro`. يدل هذا على أن تمرير البادئة ضمن `modelID` يكررها، **لكنه لا يثبت وحده أن OpenCode 1.19.5 معطوب أو أن إعادة بناء الفهرس هي العلاج**: قد يعبّر نص الخطأ عن المعرف المؤهل الطبيعي. يجب مقارنة `/provider` و`/config/providers` وإعدادات Native/CLI ونموذج يعمل فعليًا، ثم اختبار `modelID` القصير مع `providerID` الصحيح في Native مباشرة. لا تعديل لـGateway لتخمين المعرف، ولا تغيير `auth.json` أو قاعدة Native.
- **الخطوة التالية:** تشخيص غير هدّام لتباين فهرس/تكوين النموذج مع `models --refresh` فقط إن أثبتت وثائق/مساعدة نسخة CLI المحلية دعمه وأثره؛ لا إعادة تشغيل OpenCode أو مسح Cache/State دون حفظ حالة وإذن؛ ثم اختبار رد حقيقي. إن بقي عائق Native، سجّله FAIL/BLOCKED وانتقل لإصلاح 401 بصورة مستقلة. منع سقوط الجلسة لا يعني تعطيل المصادقة. جميع الفحوص Playwright حقيقية عبر LOCAL `8080`، مع HTTP/Native evidence.
- **حالة المذكرة:** هذا تحديث توثيقي في GitHub `updates` و`master` فقط؛ لا دليل على نسخه إلى جهاز Windows ولا رفع لأي كود LOCAL، ولا تغيير TEST/LIVE.

**أولوية LOCAL:** (1) Model Not Found و401، (2) Native session create/delete + رد SSE حقيقي، (3) إصلاح Refresh/navigation بوصفه خللًا وظيفيًا لا Cache، (4) بقية Native Tools/Files/Permissions، (5) اختبار التسجيل/Resend والحماية المطلوبة، (6) قياس وتحسين الأداء الشامل لاحقًا. قياسات PASS القديمة ليست إثباتًا بعد التغييرات اللاحقة. كل اختبار Playwright يذكر URL/route، HTTP، Native evidence، زمن حقيقي، وPASS/FAIL/BLOCKED؛ لا Mock و204 بوصفهما جواب AI.

## القرار الحالي: الوظائف والسرعة أولًا، ثم الحماية المتقدمة
- الهدف: نفس **الإمكانات الحقيقية** و**سرعة الاستجابة** لتطبيق OpenCode المحلي، ولكن داخل تصميم Gateway الموجود؛ **لا نستخدم واجهة OpenCode Web** ولا ننسخها.
- ترتيب العمل الإلزامي: **(1) تشغيل محلي مباشر مع Native على loopback → (2) رسالة ورد حقيقي → (3) استكمال كل وظائف Native → (4) اختبار نفس الوظائف على TEST → (5) حماية متقدمة وعزل متعدد المستخدمين قبل LIVE**.
- لا تضيف طبقات مصادقة لكل استدعاء AI، ولا تحميل فهارس كاملة مع كل صفحة، ولا AI proxy أو queue أو retry من Python، ولا محرك منفصل لكل Workspace.
- **حدود الوصول:** لا يُلغي الفصل المباشر تسجيل الدخول أو حقوق ملكية المشاريع. مسارات Native تمر عبر Nginx مباشرة بعد آلية وصول موثوقة منفصلة عن مسار تنفيذ AI؛ لا تدخل Python في طلبات Native ولا في SSE. في TEST العام يجب أولًا إثبات عدم استطاعة مستخدم الوصول إلى جلسات أو ملفات أو مفاتيح الآخرين، وألا تنكشف Native الخام أو الأسرار للجمهور. إذا تعذر إثبات العزل يُسجّل BLOCKED ولا يُفتح المسار العام.

## المسؤوليات الثابتة
- **OpenCode Native الأصلي وحده:** provider/model catalog، اعتماد API/OAuth الأصلي، الوكلاء، المحادثات/الرسائل، `prompt_async`، SSE، Todo، أدوات Shell/Read/Write/Edit، الأسئلة/الأذونات، الحفظ، الملفات والوسائط التي يدعمها فعليًا.
- **Gateway Python للإدارة فقط:** التسجيل والدخول والتحقق بالبريد، المستخدمون والأدوار والاشتراكات والفوترة، GitHub الإداري، ملكية المشاريع ومساحات العمل وبيانات ملفات المشروع وحصصها. لا Python في `Native create/list/delete session` أو اختيار model/agent أو إرسال prompt أو استقبال SSE أو إدارة API Keys الأصلية أو تشغيل Tools/Todo/Questions/Permissions. البيانات المرجعية الإدارية ليست حالة AI موازية.
- **التخزين:** `opencode.db` و`auth.json`/إعدادات Native يديرها OpenCode نفسه؛ لا SQL مباشر ولا قاعدة AI موازية. PostgreSQL منفصلة لـGateway LIVE `opencode_gateway` وTEST `opencode_gateway_test` فقط.
- **الواجهة:** نحتفظ بتصميم Gateway وRTL العربية والإنجليزية، ونُظهر كل وظائف Native الأصلية وحالاتها؛ لا ردود وهمية أو أدوات شكلية.

## قرار واجهة المزودين — حذف مفتاح API فعليًا لا مجرد فصل (4 نوفمبر 2026)
- زر المزود المدفوع يكون باسم **«حذف مفتاح API»** (Delete API Key) وليس «فصل» أو «فصل/حذف»؛ عند تأكيده يبدأ حذف الاعتماد الخاص بهذا المزود من **مخزن OpenCode Native الأصلي** باستعمال `DELETE /auth/{provider_id}` وفق ما تدعمه النسخة المثبتة. لا يكفي `account_audit` من نوع `native-provider:...:off`، ولا `gateway_disconnected` ولا إخفاء المزود في UI.
- معيار النجاح: استجابة Native تؤكد الحذف، ثم **فحص مستقل غير كاشف للأسرار** يثبت عدم وجود الاعتماد في مخزن Native. بعدها تحديث عرض Connections/Workspace من Native وإبطال بيانات العرض المتأثرة، **دون اعتبار سجل ملكية API Key داخل Gateway مصدرًا للحقيقة أو شرطًا لتنفيذ Prompt**. عند الفشل تُعرض حالة خطأ صريحة ولا يُعلن الحذف.
- **حذف مفتاح API لا يعني حذف تعريف المزود أو النماذج من فهرس OpenCode**. قد يظل `deepseek` ظاهرًا في `/provider` أو `/config/providers`، أو قد تظل `/provider.connected` قديمة بسبب الكاش أو اعتماد من البيئة؛ لذلك وجود معرف المزود ليس إثبات بقاء المفتاح.
- في LOCAL الذي يديره المطور يمكن اختبار حذف واعادة ربط **مفتاح اختبار مملوك له فقط**. قبل تجربة حذف المفتاح، احصر مصدر الاعتماد الفعلي (Native auth.json أو متغيرات البيئة أو provider plugin/OAuth) دون طباعة المفتاح. لا تمس مفاتيح الحسابات الأخرى أو LIVE؛ لا تُحاول مسح مخزن Native كاملاً.
- إذا سبق تسجيل `:off` في `account_audit` بينما بقي المفتاح في Native، هذه **حالة عدم تطابق** يجب إصلاحها داخل التدفق الفعلي، وليس بالادعاء أن المزود حُذف أو بإضافة طبقات إدارية بديلة.
- زر حذف API Key يختص بالاعتماد؛ لا يحذف Agent أو Native Session أو محادثات أو ملفات المشروع. لا تُنشئ Provider Manager جديدًا في Python. الأولوية لإصلاح ربط/حذف Native محليًا والاختبار من واجهة Playwright، ثم اعتماد التغيير في TEST بعد نجاحه.

### المبدأ
- **OpenCode Native يبقى المصدر الوحيد للحقيقة.** تبويب Dashboard → Connections هو **واجهة وقائمة مشتركة مؤقتًا** للبيانات التي جُلبت أصلًا من Native، وليس قاعدة بيانات Provider/Agent بديلة أو مخزن اعتماد آخر.
- عند فتح Workspace أو الانتقال بين المشاريع/الجلسات، تُقرأ قائمة المزودين والنماذج والوكلاء من **OpenCode Native نفسه**، مع إعادة استخدام وصف كتالوج موثوق في واجهة العميل عند الحاجة فقط، وليس من مخزن AI خاص بـGateway؛ لا يُحمّل `/provider` الكامل أو `/agent` في كل تنقل ولا يُمرّر عبر Python.
- يجوز إعادة استخدام بيانات **الكتالوج الوصفية فقط** لمدة مقترحة **7 أيام قابلة للتعديل حتى 10 أيام** مع زر تحديث يدوي، ونسخة آخر بيانات موثوقة عند التنقل؛ هذا **ليس TTL لصلاحية API key أو صلاحية اتصال أو حق مستخدم**. لا تخزن المفاتيح أو OAuth tokens في المتصفح ولا تضف قاعدة AI؛ إن استُخدم تخزين محلي آمن للميتا-داتا وحدها، فلا بد من فصلها حسب الحساب والبيئة وNative version، ومدة انتهاء واضحة.
- عند ربط/حذف مفتاح، تغيير Agent/Models/Permissions أو تغيير الحساب أو سياسة الإدارة، **تُبطل حالة الاتصال والاختيارات المتأثرة فورًا** وتُحدّث من Native (أو تعتمد حدث Native الموثوق)، دون الانتظار 7 أو 10 أيام. يظل التحقق التنفيذي الحقيقي من حالة Native عند الإرسال قائمًا، لكنه لا يستوجب إعادة تحميل قائمة 7MB كاملة مع كل Prompt.
- Agents قد تتغير باختلاف `directory` أو Workspace/Project أو Native plugins/config؛ يجب **عدم** عرض Agent خاص بمشروع آخر اعتمادًا على نسخة عامة قديمة. استخدم مخزونًا مشتركًا للحساب فقط للقدرات العامة، وبيانات مخصصة للمشروع عندما يلزم، وتحديثًا قصيرًا ومحددًا عند تغير المشروع/التكوين.
- الهدف هو تقليل زمن التنقل بين Dashboard وProjects وWorkspaces، وتحسين أول ظهور للتطبيق، ومنع polling غير المحدود ونداءات `/api/plans` المتكررة، وقياس Network requests وTime-to-Interactive وأول Token قبل/بعد. لا تسرّع الواجهة ببيانات مزيفة أو قديمة تُخفي disconnect.

### شواهد المصدر قبل التنفيذ
- يوجد حاليًا `catalogSnapshot` و`agentsSnapshot` في `app.js` مع فصل حسب مالك الحساب وإبطال بعض الحالات. لكن `native-session-client.js` يثبت `directSessionTransport=()=>false` ويعيد اكتشاف `provider/agent` من مسارات workspace؛ و`discovery()` يخزن snapshot لكل Workspace مدة 60 ثانية. لذلك الربط بين Connections وWorkspace **غير مكتمل وظيفيًا** في المصدر الجاري؛ لا تكرر إنشاء مخزن Catalog جديد، بل أصلح إعادة استخدام المصدر الموجود عندما يأتي وقت المرحلة.
- اختبر أولًا كل مراحل Native السابقة؛ **بعدها فقط** كلّف DeepSeek مرحلة التخزين المؤقت والتنقل في LOCAL، وقارن بالـTEST بعد النجاح. لا تغيير الآن في LIVE أو تشغيل خدمات جديدة.

## مرحلة مؤجلة — تأكيد البريد والحساب غير المفعّل وتجربة التسجيل (بعد انتهاء مهام DeepSeek الحالية)
**الحالة: طلب مالك معتمد مؤجل التنفيذ.** لا يُطلب من DeepSeek مقاطعة إصلاحات Native/Conversation/API Keys الحالية. بعد الانتهاء منها تبدأ جولة مستقلة لفحص هذه الرحلة ثم إصلاح النواقص، دون إضافة خدمة تسجيل ثانية.

### ما يظهر موجودًا بالفعل في مصدر `updates` عند مراجعة 4 نوفمبر 2026 — لا يعد إثبات E2E
- المسار الرئيسي لتسجيل البريد وكلمة المرور `POST /api/auth/register` يستعمل `registration_drafts.start()`: ينشئ `PendingRegistration` مؤقتًا **دون User فعّال**؛ وتؤدي `POST /api/auth/registration/confirm` إلى إنشاء `User.status=active` بعد رمز صحيح فقط. يظهر أيضًا مسار تراثي لحساب `User.status=pending_email` غير مفعّل؛ لا تفرض استبدال الآليتين أو ترحيلهما قبل الفحص، وكلاهما مقبول إن كان الحساب غير الموثق ممنوع الدخول.
- رمز OTP صالح **60 ثانية** فعلًا (`CODE_LIFETIME=60s`)، ولإعادة الإرسال Cooldown مدته 60 ثانية مع حدود محاولات/عدد رسائل (`registration_drafts.resend`). صلاحية **طلب التسجيل المؤقت ساعة** غير صلاحية رمز الـ60 ثانية. بعد انقضاء الرمز يبقى الطلب قابلًا للإرسال مجددًا وفق السياسة حتى انتهاء الطلب؛ لا تخلط بينهما.
- واجهة `app.js` تعرض عدًّا تنازليًا وخيارات **إعادة إرسال الرمز / تعديل بيانات التسجيل بما فيها البريد / إلغاء التسجيل / الرجوع لتسجيل الدخول**. التعديل عبر `PATCH /api/auth/registration/update`، والإلغاء عبر `POST /api/auth/registration/cancel`. عند تغيير البريد يرسل رمز جديد ويلغى رمز البريد السابق ضمن نفس تحدي التسجيل، ويجب إثبات ذلك بالاختبار.
- الاستعادة على الجهاز نفسه عبر `GET /api/auth/registration/pending` وHttpOnly draft cookie، **من دون إرسال رسالة جديدة تلقائيًا** أو كشف طلبات أشخاص آخرين. مسار الحساب القديم `pending_email` يدعم إعادة الإرسال بعد التحقق من كلمة المرور عبر `POST /api/auth/resend-verification`.
- `email_delivery.py` يدعم Resend عبر HTTPS API والإعدادات الحالية. وجود الكود/اختبارات pytest وjsdom وحده لا يثبت أن رسالة Resend حقيقية وصلت أو أن المتصفح أكمل التحقق؛ مطلوب Playwright وبريد اختبار مصرّح به.

### تجربة المستخدم المطلوبة عند بدء هذه المرحلة
1. حقول واضحة ومستقلة: **الاسم الكامل للعميل (Full Name)**، **اسم المستخدم (Username)**، البريد الإلكتروني، كلمة المرور وتأكيدها، مع بقاء الحقول الإدارية اللازمة للتسجيل حسب السياسة. لا تستعمل الاسم الكامل كـUsername تلقائيًا، ولا تُسقط قيمة الاسم الكامل. افحص موديل `User` والمخطط والترحيلات أولًا لإضافة الحقل فقط إن لم يكن مدعومًا؛ لا تنشئ نظام حسابات ثانٍ.
2. إذا بدأ صاحب الطلب التسجيل ولم يؤكد البريد، ثم عاد، تظهر له رسالة واضحة: **«لديك طلب تسجيل لم يكتمل. هل تريد تأكيد بريدك الآن؟»** مع زري **«متابعة التحقق»** و**«تعديل البريد أو البيانات»** و**«إلغاء الطلب»**. لا تنشئ طلبًا أو ترسل رمزًا جديدًا تلقائيًا بمجرد العودة.
3. إذا كان سجل User تراثيًا بحالة `pending_email`، يجوز الاحتفاظ به غير مفعّل ثم تغيير حالته إلى `active` بعد تأكيد البريد الصحيح؛ لا تُنشئ User آخر لنفس الهوية. لا يُمنح حساب `pending_email` أي صلاحيات عميل أو جلسة كاملة قبل التحقق.
4. لا تكشف عبر نموذج عام غير موثق أن عنوان بريد يخص شخصًا آخر أو أن حسابه ينتظر التفعيل. اعرض خيار «حسابك يحتاج تأكيدًا» **فقط بعد إثبات ملكية الطلب** بملف draft cookie السري أو هوية المستخدم وكلمة مروره أو إثبات بريد رسمي. لبقية الحالات استعمل رسالة عامة لا تسهّل حصر الحسابات.
5. بعد إرسال الرمز عبر Resend، اعرض شاشة تحقق فيها عنوان البريد المرسل إليه **بعد إثبات ملكية الطلب**، عدّ تنازلي مرئي يبدأ من 60 ثانية، حقل OTP من 6 أرقام، وزر تأكيد. يجب أن يعكس العداد وقت انتهاء الرمز الذي يعيده Backend، لا عدّادًا تجميليًا فقط.
6. عند عدم وصول الرمز أو انتهاء صلاحية الـ60 ثانية: زر **«إعادة إرسال الرمز»** يصبح متاحًا بعد مهلة الإعادة وتأكيد الإرسال من الخادم؛ لا تعيد الإرسال تلقائيًا. زر **«تعديل البريد الإلكتروني»** يعيد التحقق إلى العنوان الجديد ويُلغي الرمز السابق؛ زر **«إلغاء التسجيل»** يلغي الطلب المؤقت فقط ولا يحذف حسابات مفعّلة. وضّح أسباب فشل Resend والحدود دون كشف مفاتيح أو رموز.
7. بعد تأكيد الرمز الصحيح لأول مرة فقط: أنشئ/فعّل الحساب النهائي، ابدأ الاستحقاق التجريبي حينها فقط، ثم اسمح بجلسة الدخول. أعد التحقق من تفرد Username/Email قبل الالتزام النهائي، ولا تسمح بتكرار التفعيل أو الاستحقاق عند تكرار الطلبات.
8. عند التسجيل المعلق وصلاحية الرمز المنتهية والعودة بعد Refresh/Logout/إعادة الدخول، يجب أن تعمل خيارات المتابعة/تعديل البريد/إلغاء الطلب دون فقد الطلب أو إنشاء مستخدم مكرر، ما دامت صلاحية الطلب تسمح. عند انتهاء صلاحية الطلب نفسه، اشرح وجوب بدء طلب جديد.
9. اختبارات Playwright الحقيقية تشمل: نجاح رمز خلال 60 ثانية، فشل رمز منتهي/خاطئ، إعادة الإرسال بعد المهلة، حد إرسال محمي، تغيير البريد وإبطال الرمز القديم، إلغاء الطلب، استعادة طلب قائم، حساب قديم `pending_email`، منع دخول/صلاحيات قبل التفعيل، تفرد Username والبريد، وعدم كشف حالة حساب غريب، Resend عبر صندوق بريد اختبار حقيقي. سجّل PASS/FAIL/BLOCKED مع أدلة HTTP/DB ووقت السيناريو؛ لا Mock بوصفه اختبار تسليم نهائي.

### ترتيب التنفيذ
- **أولًا** يكمل DeepSeek المهمة الجارية على LOCAL فقط: مطابقة معرفات النموذج، استقرار جلسة الدخول 401، إنشاء/حذف Native Sessions، ثم Todo/Tools/Permissions/Files والاختبارات الحقيقية. لا يبدأ مرحلة Cache الشاملة قبل إكمال الوظائف الأساسية. وتصحيح Refresh الذي يعيد الصفحة إلى Workspace خلل وظيفي مستقل يُصلح دون إعادة هندسة التخزين المؤقت.
- **ثانيًا** بعد تقديم نتائج تلك المرحلة، يُعطى DeepSeek تكليفًا مستقلًا لتدقيق وتنقيح الرحلة الموضحة أعلاه؛ لا يبدأ الآن، ولا تعدّل TEST/LIVE أو `master` دون اعتماد ونشر آمن.
- **ثالثًا** يأتي تحسين التخزين المؤقت لمدة 7–10 أيام والتنقل الشامل وفق المرحلة المؤجلة السابقة.
