# نقل إصدار TEST إلى LIVE — دليل تنفيذ آمن
**الهدف:** تطبيق الواجهة والـBackend ومسار Native First نفسه في LIVE مع بقاء نطاق الإنتاج `https://opencode-gateway.codes` على Gateway المنفذ `8000` وقاعدة `opencode_gateway`. يبقى TEST على `test.opencode-gateway.codes` والمنفذ `8001` وقاعدة `opencode_gateway_test`.

## حدود النشر
- لا ننقل ملفات `.env` الخاصة بـTEST إلى LIVE، ولا ننسخ قاعدة TEST فوق LIVE، ولا نمس أسرار الربط البنكي وGitHub وSMTP والتشفير.
- تُطبّق تحديثات قاعدة الإنتاج باستخدام `alembic upgrade head` بعد نسخة احتياطية PostgreSQL مستقلة. يبقى ربط كل حساب ببيانات LIVE كما هو.
- يُنسخ إصدار التطبيق المتطابق مع الواجهة الموجودة فعليًا على TEST؛ يرفض سكربت النشر وجود اختلاف في ملفات الواجهة الأساسية.
- لا نغيّر توجيه الدومين أو SSL أو IP أو Nginx server{} الأصلي، بل نضيف موقعَي Nginx داخليين في كتلة LIVE الحالية.
- OpenCode Native خدمة واحدة قائمة على `127.0.0.2:4097`، وممران داخليان `18097/18098`، وPython يفوض كل طلب ولا يستقبل رد الذكاء الاصطناعي أو SSE.
- LIVE وTEST قاعدتان ومجلدا مشاريع منفصلان. استخدام Native واحد لا يضمن بحد ذاته فصل مفاتيح النماذج على مستوى العملية الواحدة؛ هذا الشرط **غير معتمد للعملاء الحقيقيين حتى اختبار العزل**.

## قبل النشر
1. مراجعة `/etc/nginx` على VPS وتحديد كتلة HTTPS الخاصة بـ`opencode-gateway.codes` دون تخمين اسم الملف.
2. إضافة محتوى `docs/NATIVE_SESSION_LIVE_NGINX.conf` *داخل تلك الكتلة فقط*. إبقاء `location /` ومساره إلى LIVE Gateway:8000، وشهادة SSL والتوجيهات الأخرى دون مساس. تطبيق `sudo nginx -t` ثم `sudo systemctl reload nginx` بعد نجاح التحقق.
3. التأكد من أن `/home/tahir/opencode-gateway/.env` يحمل الدومين وبيانات LIVE الأصلية، بما فيها اسم قاعدة الإنتاج ومفتاح التشفير. لا تلصق محتواه في GitHub أو المحادثة.
4. التأكد من أن Native الحالي، ووكيلَي Nginx الداخليين، وملفات TEST الأصلية تعمل، ولا تنفذ ترقية لإصدار OpenCode نفسه أثناء النقل.
5. مراجعة ودمج PR #17 بعد نجاح CI، ثم تشغيل Workflow `Promote approved Native First source to LIVE` يدويًا من `master` باستخدام الكلمة `promote`.

## ماذا يفعل Workflow
- يثبت SHA واحدًا من master للاختبار والنشر.
- يرفع ملفات المصدر إلى `~/opencode-gateway-release` عبر SSH باستثناء الأسرار وبيانات التشغيل.
- يرفض النقل إذا تعارض الدومين أو اسم قاعدة LIVE أو منفذ Gateway أو إعدادات Nginx أو خدمات Native أو ملفات واجهة TEST مع المصدر.
- **خلال النقل الحالي فقط بناءً على طلب المالك:** لا ينشئ أي نسخ احتياطية ولا يحذف الملفات القديمة. يتم إنشاء نسخ احتياطية بعد إثبات نجاح LIVE وفق إجراء مستقل.
- ينسخ الكود، ثم يحدث **مفاتيح تشغيل Native فقط** في ملف بيئة الإنتاج، ويشغّل Alembic ويعيد تشغيل `opencode-gateway.service`؛ لا ينشئ خدمة OpenCode ثانية.
- يتحقق من `http://127.0.0.1:8000/api/health` و`https://opencode-gateway.codes/api/health`.

## قبول الإنتاج
اجتياز HTTP 200 غير كافٍ. يلزم التحقق بتسجيل دخول حقيقي في دومين LIVE من: إنشاء مشروع/Workspace، الربط بـGitHub والدومين الصحيح للـOAuth، فتح محادثة Native، اكتمال رد النموذج والبث SSE، الأدوات والمرفقات، تغيير المزود/الموديل، ملكية ملفات ومحادثات مستخدمين منفصلين، واستمرار جلسات TEST دون اختلاط. لا تطلق المشروع لعملاء حتى ينجح عزل مفاتيح المزودين داخل Native المشترك.

## في حالة فشل النشر
اترك TEST وقاعدته دون تغيير. افحص مجلد النسخ الاحتياطية الموضح في سجلات Job، وسجل الخدمة وسبب رفض الفحص. لا تُنفّذ إعادة تهيئة قواعد البيانات، ولا تسترجع dump على قاعدة الإنتاج دون خطة استرجاع دقيقة؛ قد تكون Alembic نجحت قبل تعثر تشغيل الخدمة. ولا تشغّل Workflow الإنتاج القديم الذي يتحقق من منفذ `4096` غير المستخدم.
