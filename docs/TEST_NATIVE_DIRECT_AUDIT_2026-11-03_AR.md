## الفجوات الحقيقية التي لم تغلق

1. **مخزن الاعتمادات المشترك:** OpenCode 1.19.4 في هذا التثبيت يطبّق /auth على مستوى العملية. `directory` لا ينشئ مفتاحًا خاصًا بكل حساب. مستخدمان بنفس المزود لكن بمفتاحين مختلفين لا يمكن فصلهما عبر هذا API وحده. لا تزعم إتمام عزل العملاء، ولا تختبر ذلك بمفاتيح حقيقية لأشخاص آخرين.
2. **مسار /native-direct/api له Basic Auth واحد:** لا يحقق حق ملكية `user → project → workspace → session`؛ ولو كان تنفيذ النموذج مباشرًا. ينبغي فصل هوية العميل والتحقق من ملكية الموارد قبل إتاحة Native للمستخدمين على نطاق أوسع. لا تحاول علاج ذلك بإعادة كتابة رد SSE عبر Python.
3. **حالات "connected" الوهمية:** `/provider.connected` يثبت وجود اعتماد في عملية Native فقط، لا ملكية الحساب أو صلاحية المفتاح لدى المزود. يجب أن تعرض الواجهة هذه الحالة "محفوظ في Native / غير متحقق"، لا "متصل ومدفوع ويعمل".
4. **مفاتيح Gateway التاريخية:** منع POST الجديد عبر Python في TEST لا يعني حذف صفوف `user_provider_credentials` القديمة. لا حذف جماعي أو إعادة تشفير بلا تدقيق ملكية ومقارنة مفاتيح وعدّادات فقط. طلب المالك إبقاء DB دون تغييرات.
5. **كل خدمات الأدوات:** وظائف Native المباشرة للأدوات والموافقات تحتاج اختبارًا فعليًا لكل فئة (قراءة/كتابة/بحث/سطر أوامر/صور ومرفقات/مهام/أسئلة) داخل مشروع حقيقي، لا يكفي اختبار النص.
6. **الأذونات والعمليات:** تخويل الوصول للأدوات والملفات ضمن عملية مشتركة يحتاج عزلًا فعليًا. لا تفترض أن `directory` في رابط HTTP حاجز أمني.
7. **الأداء:** لا تعاود قراءة كتالوج 7 ميجابايت قبل كل رسالة، ولا تضف اختبار مفتاح عند كل prompt؛ اختبر الربط مرة عند إضافة المفتاح فقط. يمكن قياس TTFB وSSE ومعدل تحميل الكتالوج قبل أي تحسين لاحق.
