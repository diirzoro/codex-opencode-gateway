## 1. الهدف والقرارات الثابتة
- الاستغناء تدريجيًا عن OpenCode **في TEST فقط أولًا** واستبداله بـPi Coding Agent.
- تشغيل محرك Pi **مركزي واحد** يخدم لاحقًا TEST وLIVE، مع فصل ملكية المشاريع والجلسات والملفات وعدم مزج قواعد البيانات. لا تفعيل LIVE في هذه المرحلة.
- Nginx مفتاح التوجيه؛ إبقاء الدومينات ومسارات الواجهة والمنافذ العامة كما هي. `8000` للـLIVE Gateway، `8001` للـTEST Gateway.
- الاحتفاظ بقاعدة TEST المنفصلة، حسابات المستخدمين، صلاحياتهم، إدارة المشاريع، GitHub، الفوترة، وعناصر Dashboard.
- **الأولوية السرعة ثم الأمان**: Pi الأصلي يدير المحادثات والأدوات؛ Node.js فقط HTTP/SSE ↔ RPC. Python يبقى لخدمات إدارة المنصة الحالية ولا يدخل في تنفيذ الذكاء.
- لا إنشاء `releases` أو نسخ Backups إضافية أثناء الربط. الإبقاء على إصدار TEST الحالي. لا حذف أو إيقاف خدمة OpenCode المشتركة حتى اكتمال التحويل.
- نموذج العمل: مشروع واحد = جلسة Pi واحدة دائمة، لا توليد جلسة جديدة في كل Refresh.
- عدم إعلان اتصال المزود «Verified» بمجرد ظهور النماذج أو نجاح حفظ المفتاح؛ يلزم نجاح رد AI فعلي لتأكيد الاعتماد.

## 11. خطة التنفيذ المفصلة: Gateway + Pi — 2026-11-10

> **قرار المالك الأحدث:** هذا القسم يتقدم على أي عبارة تاريخية أعلاه تجعل Pi أو OpenCode مالك مفاتيح العميل أو تجعل تحميل قائمة النماذج معتمدًا على اكتشاف المحرك في كل فتح. المذكرة خطة تنفيذ وليست شهادة إنجاز؛ يُحدَّث وضع كل مهمة بعد اختبارها الحقيقي.

### 11.1 التصميم الثابت: أربع ركائز

1. **A — Gateway-owned Providers & Connections:** Dashboard وGateway يملكان فهرس المزوّدين واتصالات كل عميل. تعرض Workspace الاتصالات المملوكة لذلك العميل بالضبط؛ لا تُجري إدارة الاتصالات عبر Pi ولا عبر كتالوج عام.
2. **B — Verified & Revocable Credentials:** Gateway يتصل بالمزوّد الحقيقي للتحقق من صلاحية مفتاح API، ولا يحفظ اعتمادًا موصوفًا بالتحقق قبل إثبات المصادقة. يُخزَّن السر مشفرًا، ويمكن لصاحبه إزالة الاتصال والمفتاح في أي وقت؛ لا تعود بياناته بعد Refresh أو تشغيل عامل Pi آخر.
3. **C — Provider-scoped Cached Model Catalog:** حفظ فهرس المزوّدين والنماذج في PostgreSQL التابعة للمشروع، بعلاقة كل نموذج مع مزوّده. التحديث الدوري كل **7 أيام افتراضيًا، ولا يُسمح بتجاوز 14 يومًا دون إظهار تنبيه واضح**؛ تحميل الصفحات والبحث من قاعدة Gateway فورًا دون تنزيل كتالوج Pi كاملًا. فهرس عام ≠ اتصال مستخدم.
4. **D — Isolated Pi Coding Engine:** تستلم جلسة Pi فقط المزوّد والنموذج والاعتماد المختار من الاتصالات المصرح بها في Gateway، مع سياق معزول لكل عميل؛ لا يحفظ Pi مفتاح العميل في `auth.json` المشترك. يظل Pi وحده مسؤولًا عن المحادثات، قراءة/تعديل الملفات، Bash، Tools، Skills، Extensions، وأحداث التنفيذ.

**مثال إلزامي:** المفتاح الفريد للنموذج ليس `model_id` وحده بل `(provider_id, model_id)`. `openrouter / deepseek-chat` لا يساوي `deepseek / deepseek-chat` ولو تشابه الاسم؛ لا تتحول نماذج مزوّد إلى اتصالات مباشرة بمزوّد آخر. تشمل العلاقة معرّفات المزود الأصلية وربما `api_variant` عند حاجة Pi؛ تعرض الواجهة الاسم البشري دون التضحية بالهوية الفنية.

**تدفق العمل المستهدف:**
`Dashboard Connections → Gateway authenticated account connection → validated encrypted secret in Gateway DB`
`Dashboard + Workspace → Gateway DB: my connected providers + public models per provider`
`Workspace selects (provider_id, model_id, connection_id) → Pi Central internal authorization → isolated Pi SDK runtime/session → real upstream provider`

**موضع الإصلاح:** `backend/app/routes/management.py` و`backend/app/main.py` ونموذج موجود في `backend/app/models/` و`app.js` و`management.js`؛ مراجعة `integration/pi-central.mjs::scope`.

**A1 — ملكية البيانات وعقود API:**
- عقد بيانات معياري للمزوّد العام `provider_id` واسم العرض ونوع طريقة الاتصال؛ وعقد مستقل لاتصال العميل `connection_id, user_id, provider_id, auth_type, auth_status, verified_at, last4`. يُشتق `user_id` من جلسة الخادم لا من `query/body`.
- طلبات Gateway المقترحة ضمن `/api/account/ai-connections`: `GET` لاتصالاتي، `POST` إضافة/تحقق، `DELETE /{connection_id}` حذف، `POST /{connection_id}/reverify` إعادة تحقق؛ صياغة دقيقة متوافقة مع مسارات المشروع القائمة وتفويضاتها. لا يُعاد فتح `/api/opencode/connections` القديم أو إدخال Python في تنفيذ المحادثات.
- تأمين عزل المستخدمين داخل backend نفسه. الـNginx `auth_request` وحده ليس إذنًا لتغيير اتصال. إزالة/تقييد كل مسار مشترك `CATALOG_DIRECTORY / userId:"shared"` يستطيع كتابة اعتمادات Pi.

**A2 — Dashboard ⇄ Workspace:**
- قسم `Connections` في `management.js` هو المرجع الوحيد لربط/حذف مزود العميل. `Workspace` يسحب «اتصالاتي» من Gateway نفسها؛ يحدّث الاختيار بعد الربط والحذف وتبديل الحساب دون Refresh كامل عندما يمكن.
- يعرض `provider_id` و`model_id` الحقيقيين معًا، لا يخلط المزوّد العام بالاتصال. المزود موجود في البحث حتى لو لم يربطه العميل، لكن لا يُقدَّم كخيار تنفيذ باسم العميل إلا باتصال صالح أو تصريح واضح لمفتاح المنصة الافتراضي.
- تتغير `backend/app/main.py::browser_boundary` وقواعد `app.js::nativeDirectTest.route` بصورة محددة حتى تعمل واجهات اتصالات Gateway الجديدة، مع إبقاء مسارات Pi للتنفيذ فقط. لا fallback إلى محرك AI Python.

**قبول A:** حسابان مستقلان، لا يرى الأول اعتماد الثاني أو يحذفه، وWorkspace تعرض اتصالات الحساب الظاهرة في Dashboard ولا تعتبر الكتالوج دليل اتصال. لا نص مفتاح أو Hash قابل للاسترجاع في API القراءة.

### 11.5 B — مهمة Work: تحقق مفتاح حقيقي، حفظ مشفر، حذف دائم من اتصال العميل

**موضع الإصلاح:** `backend/app/routes/management.py`، `backend/app/services/credentials.py`، نموذج موجود في `backend/app/models/`، `management.js`، ومسارات `runtime.login/logout` الحالية داخل `integration/pi-central.mjs` عند القطع النهائي.

**B1 — التحقق قبل الحفظ:**
- لكل مزوّد مدعوم endpoint رسمي للمصادقة بمفتاح العميل (قد يكون metadata أو balance endpoint مصادقًا، أو استدعاء صغير إذا لم توجد واجهة تحقق مناسبة). تعطي المصادقة الناجحة `verified_auth` **لا** «رصيد مؤكد» أو «كل النماذج قابلة للتشغيل».
- `401` أو رفض مصادقة صريح ⇒ `invalid_key`، ولا حفظ. `402`/رصيد غير كافٍ مع ثبوت المصادقة ⇒ `insufficient_balance` منفصل، لا يعتبر مفتاحًا وهميًا. `403` قد يعني عدم صلاحية محددة؛ `429` تعني حدود استخدام؛ timeout/خطأ الشبكة ⇒ `unverified`، ولا ادعاء بصلاحية أو فساد المفتاح. خطأ نموذج غير متاح ليس خطأ مفتاح.
- إذا لم تتوفر آلية تحقق موثوقة لمزوّد معين، يُعرَض `unsupported_verification` مع منع الادعاء بالتحقق أو الحفظ المعتمد؛ تدفق OAuth منفصل ويحتاج دعمًا مثبتًا.
- تحقق HTTPS بخوادم محددة لا URL يدخله العميل (منع SSRF)، حدود معدل/مهلة/حجم واستجابة آمنة، وعدم تسجيل المفتاح أو إرجاعه. ولا إرسال Prompts مدفوعة دون إيضاح ذلك للمستخدم.
- بعد نجاح الاختبار، تشفير server-side بواسطة آلية المشروع `backend/app/services/credentials.py` بمفتاح بيئة خارج DB، ثم كتابة سجل **خاص بالعميل** ومعاملة واحدة؛ فشل التخزين لا يسجل اتصالًا ناجحًا.

**B2 — حذف المفتاح أو تغييره في أي وقت:**
- `DELETE` عبر اتصال المستخدم نفسه، بحذف سجله المشفر أو إبطال استعماله فورًا ومنع استرجاعه بعد Refresh/Login؛ الاستجابة لا تُعلن نجاحًا قبل تأكيد العملية على قاعدة البيانات. تحديث كل اختيارات Dashboard/Workspace وذاكرة Pi ذات الصلة.
- إبطال أو إيقاف الطلب الجاري الذي يستخدم المفتاح القديم وفق قدرة Pi؛ **لا نجاح كاذب** إن كان العامل لا يزال يحتفظ باعتماد قابل للاستعمال. الحذف من Gateway لا يعني إبطال المفتاح من حساب الشركة المزوّدة ما لم توفر الشركة عملية إلغاء رسمية نُفذت بالفعل.
- التغيير (rotation) يمر بتحقق جديد ثم تبديل معزول دون تعريض اعتماد المستخدم القديم إلى مستخدم آخر. حذف DeepSeek للعميل A لا يمس اتصال B أو اسم DeepSeek في الكتالوج العام.
- مفتاح OpenRouter الافتراضي الخاص بالمنصة منفصل عن BYOK؛ لا يظهر مفتاح المنصة كأنه ملك للعميل أو قابل للحذف من حسابه.

**قبول B:** مفتاح عشوائي لا يُحفظ؛ مفتاح فعلي معروف الملكية يُتحقق منه عبر المصدر الحقيقي؛ رصيد صفر حالة مختلفة؛ انقطاع الشبكة لا يصير Invalid؛ حذف المفتاح/التبديل لا يُحييه بعد تحديث المتصفح أو تشغيل جلسة جديدة؛ فصل العملاء مع اختبار مفاتيح مختلفة. جميع اختبارات المفاتيح تعتمد أسرار اختبار مصرحًا بها لا أسرار مستخدمين فعليين.

### 11.6 C — مهمة Work: كتالوج PostgreSQL سريع لكل مزوّد مع نماذجه

**موضع الإصلاح:** نطاق الـDB/ORM الحالي بعد P0، `backend/app/routes/management.py` أو مسارات عرض قائمة مناسبة، `integration/pi-central.mjs::nativeDiscovery/providerCatalog` لمزامنة المصدر وليس إدارة اعتمادات العميل، `app.js`، `runtime-client.js`، `native-session-client.js`، `management.js`، والصيانة الدورية القائمة إن أمكن **دون خدمة جديدة**.

**C1 — تصميم الفهرس المطلوب (مفاهيمي إلى حين اعتماد Schema):**
- `providers`: `provider_id` ثابت كالمصدر الأصلي، `name`، `source`، `enabled/hidden` لسياسة العرض، `last_successful_sync`، `next_sync_at`، `sync_revision`، `sync_error_category` (بدون أسرار).
- `provider_models`: مفتاح مركّب `(provider_id, model_id)`، وإيضاحات النموذج والإمكانات والأسعار/السياق فقط إذا كانت موثوقة، `updated_at`، `active`. لا صف نموذج مستقل عن المزوّد ولا اعتماد على الاسم وحده؛ لا ادعاء أن الأسعار ثابتة.
- `user_connections`: منفصلة عن كتالوج النماذج، على الأقل `id, user_id, provider_id, encrypted_key, auth_status, verified_at, revoked_at`، مع قيد ملكية/فردانية ملائم للاتصال. لا تخزين المفتاح أو حالة الـVerified في `providers`.
- الأسماء السابقة **تصميم منطقي وليست أسماء جداول مؤكدة على VPS**؛ يتم مطابقة الأعمدة والجداول الموجودة قبل أي DDL. لا استخدام جدول الفوترة أو `platform_policy` كمخزن اعتماد أو كتالوج بديل.

**C2 — التحميل والمزامنة:**
- الواجهة تبدأ بـ`GET provider summaries` خفيف من DB، ثم `GET models?provider_id=...` بتحميل كسول وترقيم/بحث خادمي؛ Dashboard وWorkspace يستخدمان نفس الفهرس ونفس اتصالات Gateway.
- منطق التحديث يستفيد من مصدر Pi الأصلي/واجهات المزوّد الرسمية لا كتالوج وهمي. تبدأ المزامنة الدورية وفق `next_sync_at` مرة كل 7 أيام، مع تنبيه وتقييم مصدر البيانات إن تجاوز آخر تحديث ناجح 14 يومًا. لا حجب للواجهة عند فشل التحديث ولا مسح آخر snapshot موثوق. تحديث تغييرات المزود/النموذج بطريقة ذرية مع رقم revision.
- تشغيل التحديث عبر الصيانة/الجدولة الموجودة **إذا أمكن دون إضافة خدمة أو ملف**؛ لا تحديث لكل Prompt أو كل فتح Workspace، ولا طلب آلاف النماذج من Pi حين يكتب المستخدم حرفًا في البحث.
- الفصل بين فهرس عام واتصالات العميل: Connected من جدول اتصالات العميل وحده، وProvider/Model availability عند التنفيذ من Pi. نماذج متشابهة عند مزودين مختلفين تبقى صفوفًا مستقلة.
- البحث محلي مفهرس، مع Debounce وإلغاء الطلبات الأقدم؛ عدّ عدد الطلبات وأحجامها ووقت فتح Connections وWorkspace والنموذج قبل/بعد. لا وعود بأرقام سرعة قبل القياس.

**قبول C:** لا تحميل كتالوج متعدد الميجابايت لمجرد فتح الصفحة؛ البحث عن مزوّد خارج أول 50 نتيجة يعمل؛ النماذج محفوظة تحت مزوّدها الصحيح؛ مزودان لهما `model_id` متشابه لا يختلطان؛ 7–14 يوم سياسة مسجلة مع حالات التأخر؛ اختيار Workspace وDashboard متزامن، ولا يُرسل أي سر ضمن الكتالوج.

### 11.7 D — مهمة Work: Pi SDK مع بيئات عمل واتصالات معزولة

**موضع الإصلاح:** `integration/pi-central.mjs`، `native-session-client.js`، `runtime-client.js`، و`backend/app/routes/workspaces.py` فقط إذا لزم الربط الإداري. لا تشغيل OpenCode آخر ولا خدمة Pi إضافية.

**D1 — تحقق SDK والعزل:**
- تثبيت عقد الإصدار الموجود على TEST: هل يدعم `ModelRuntime.create` و`createAgentSession` مع حقن credentials على مستوى الجلسة دون كتابة في `auth.json`؟ إذا لا، تُوثق حدود النسخة والخيار دون ترقية مفاجئة للمحرك المشترك.
- عند تشغيل مشروع، Pi Central يستعلم **داخليًا وباعتماد خدمة موثوق** عن إذن الحساب واتصاله المختار من Gateway؛ لا يعيد مفتاحًا سريًا إلى المتصفح ولا يستخدم Cookie الزائر كتصريح داخلي لقراءة مفاتيح أي عميل. يفحص `user_id + project_id + connection_id + provider_id + model_id` ويمنع تشغيل نموذج من مزوّد غير متصل أو غير مدعوم.
- مفتاح العميل يُسلَّم لسياق Pi الخاص بهذا العميل/المشروع في الذاكرة أو وسيلة مؤقتة آمنة مدعومة رسميًا، لا `/home/tahir/.pi/agent/auth.json` المشترك، ولا `models.json` مشترك يحتوي سرًا؛ لا إعادة استعمال `ModelRuntime` حامل المفتاح بين العملاء.
- منع تسرب الاعتمادات عبر environment الموروثة، logs، stderr، SSE، session dumps، tool outputs أو ملفات Workspace. الفصل بين مفتاح منصة OpenRouter الافتراضي وBYOK. عدم الاكتفاء بعزل اسم المجلد إذا كانت العمليات تشترك في هوية نظام التشغيل.

**D2 — التشغيل المستمر والملفات:**
- مشروع واحد/جلسة Pi واحدة مستمرة؛ مراجعة `projectIdFor` الحالي لأنه يضم `workspaceId`؛ استخدام ربط `ProjectNativeSessionBinding` الإداري دون تغيير جلسة عند Refresh أو فقد SSE. لا حذف/دمج تاريخ أو ملفات قديمة.
- Pi وحده ينفذ Tools/Read/Edit/Bash/Skills/Extensions والأسئلة/الأذونات والمرفقات، والواجهة تعرض نتائج فعلية. `HTTP 200/204` أو `health ready` ليس إثبات إكمال Prompt أو تنفيذ أداة.
- إعادة اختيار/إلغاء مزوّد من Dashboard تنعكس على قائمة نموذج Workspace فورًا؛ رفض إرسال Prompt بارتباط محذوف حتى لو كان الـUI قديمًا. التوقف/الاستئناف وحالات «receipt uncertain» لا تُنشئ جلسة جديدة.
- عزل ملفات وعمليات العملاء (مستوى نظام التشغيل أو حاوية/هوية منفصلة وقيود موارد) شرط قبل السماح بأدوات Shell لعملاء متعددين في الإنتاج. لا يُنشأ نظام نشر/خدمة جديد ضمن هذه المهمة؛ إن تعذر العزل المناسب بالإعدادات القائمة يبقى **BLOCKED for multi-tenant tools**.

**قبول D:** عميلان بمفتاحين مختلفين يشغل كل منهما نموذجًا مصرحًا؛ حذف مفتاح أثناء حياة الجلسة يمنع الاستعمال اللاحق؛ Refresh يستعيد المحادثة نفسها؛ فحص قراءة/تعديل ملف تجريبي لا يتجاوز Workspace العميل؛ أدوات وأسئلة/Skills حقيقية دون تشغيل كود AI موازٍ.

### 12.3 الدروس والتصحيحات من مذكرات 9 نوفمبر — لا يُعاد اعتبارها PASS لـPi

- **المفاتيح الوهمية:** حفظ `PUT /auth/{provider}` في OpenCode، و`runtime.login` في Pi يثبت وجود الاعتماد في المخزن فقط، لا صحة المفتاح. يتطلب الإصلاح تحققًا عند المزود قبل حفظه.
- **عودة DeepSeek:** قد يكون سبب الظهور مفتاحًا مشتركًا في ملف `auth.json`، إعدادات/بيئة المحرك، Cache أو ردًا قديمًا؛ وجود نموذج DeepSeek لدى OpenRouter ليس اتصال DeepSeek مباشرًا. المطلوب فصل «المزود متاح» عن «عميل متصل».
- **الفهرس البطيء:** وثقت النسخ القديمة فهرسًا واسعًا (235 مزودًا في إحدى التجارب)، وأظهر كود الواجهة الحالي إمكان تنزيل `/provider` بحجم 7+ MB وحد مهلة 90 ثانية؛ لا يُعاد تحميل هذا على كل زيارة.
- **حالة الطلبات:** `HTTP 200/204`، حالة `health:ready`، أو حدث `session.idle` وحدها لا تثبت نجاح AI؛ يلزم محتوى رد وأحداث نهاية أو فشل فعلي.
- **الـ404 القديمة:** `auth/deepseek` عانت تعارض توجيه بين منافذ OpenCode، كما فشلت جلسة قديمة ب`Session not found`. هذه أدلة تاريخية تخص OpenCode وليست إثباتًا أن Pi الجديد يعاني السبب نفسه؛ نفحص Pi الحالي بعقده الفعلي.
- **ما أُبلغ عن نجاحه محليًا في OpenCode:** تسجيل وOTP/GitHub/UI، Read وWrite وTodo، بعض SSE وRefresh وتحسينات البحث. لا نعيد كتابة تلك وظائف المنصة، لكن **لا نتعامل معها كاختبارات قبول Pi** حتى يثبت سلوكها بعد الانتقال.
- **ما كان مفتوحًا أو محجوبًا:** أسئلة/موافقات Native متعددة الاختيارات، Edit حقيقي، المرفقات TXT/JSON/Images/PDF، Recover/Abort، SSE بعد الانقطاع، Tools/Todo كامل، صلاحيات العملاء، GitHub Sync الفعلي، عزل عدة مستخدمين، وعودة المفتاح بعد الحذف. جميعها تُرحّل كمتطلبات قبول لا كإصلاحات مثبتة.
- **حماية العرض:** لا تُظهر سكربتات الأدوات أو القيم السرية كمحتوى ملف عند الرفع، ولا تخرج أسرارًا ضمن رسالة خطأ أو سجل. الحفاظ على تنسيق الرسائل العربية والإنجليزية الطويلة.
- **صيانة الأدمن:** افحص أن إعدادات GitHub الإدارية مرئية حسب الصلاحية وأن ربط GitHub للعملاء لا يتعطل؛ هذا احتفاظ بوظائف المنصة وليس جزءًا من محرك AI.

## 13. قيود VPS وقاعدة البيانات الحالية والتوزيع المستقبلي

### 13.1 الواقع الحالي (قرار المالك، وليس قياسات أداء)

- الخادم الواحد يحوي **1 vCPU و4GB RAM**، وتعمل عليه **PostgreSQL + Gateway Backend + Pi Central + Nginx**. لا نفترض أن قاعدة البيانات خدمة خارجية أو أن موارد Pi الخاملة تساوي استهلاكه أثناء تشغيل `npm install` أو `npm run build`.
- **الآن:** استخدام مثيل PostgreSQL القائم نفسه؛ فهرس مزوّدين/نماذج **منفصل منطقيًا** عن اتصالات ومفاتيح العملاء في جداول/نماذج صحيحة داخل قاعدة TEST الحالية، لا إنشاء خادم DB جديد ولا خدمة مزامنة جديدة.
- **مستقبلًا:** يُراعى التصميم قابلية **نقل PostgreSQL إلى خادم أو خدمة مستقلة** عندما يكبر عدد العملاء، مع فصل بيئات TEST/LIVE وصلاحياتهما. هذا **استعداد معماري فقط** وليس نقلًا/نسخًا/إنشاء قاعدة أخرى الآن.

### 13.2 متطلبات نقل قاعدة البيانات مستقبلًا دون إعادة بناء

1. تعزل جميع استعلامات Gateway DB عبر إعداد الاتصال وORM الحالي، وليس عنوان `localhost` ثابتًا داخل الواجهة أو Pi. تبقى مفاتيح API مشفرة، ومفتاح التشفير خارج DB.
2. تصميم العلاقات على مفاتيح `user_id` و`connection_id` و`provider_id/model_id`؛ لا تعتمد على تسلسل IDs محلي لقاعدة بعينها أو أسماء نماذج عامة غير فريدة.
3. عند نقل DB مستقبلًا: إعداد اتصال آمن/خاص، TLS حيث ينطبق، صلاحيات منفصلة، pooled connections، schema migrations متوافقة، نسخ بيانات آمن، نسخ احتياطية واختبار الاستعادة، ورصد latency. لا يُنفذ أي نقل الآن.
4. لا تضع تفاصيل اتصال DB أو كلمات المرور في JavaScript أو Pi Session؛ Pi Central يحصل على قرار التفويض والاعتماد المحدد عبر قناة داخلية آمنة مع Gateway، لا عبر وصول عام غير محدود إلى الجداول.
5. لا تمس بيانات LIVE أو اعتمادات العملاء/الجلسات أثناء تحضير قابلية النقل، ولا تنفذ توزيعًا أفقيًا أو Sharding اليوم.

### 13.3 ضبط Pi والـCPU والـRAM الآن — جزء إلزامي من مهمة D

**الموضع الفعلي:** `integration/pi-central.mjs` يتضمن `MAX_PROCS=Math.max(2,Math.min(32,Number(process.env.PI_MAX_WORKERS)||6))`؛ هذه القيمة **ليست مقبولة كافتراض تنفيذ ثقيل متزامن** على 1 vCPU/4GB. قم بالتالي:

- فصل **وجود جلسات Projects محفوظة** عن عدد **عمليات Pi النشطة** وعن عدد **مهام Bash/build الثقيلة الجارية**. الحد الابتدائي **مهمة تنفيذ برمجية ثقيلة واحدة في كل لحظة**. يمكن انتظار المشاريع الأخرى دون ضياع History أو إنشاء Session جديدة أو تغيير `project_id`.
- عدّل التحكم في العمال كي يدعم حدًا قابلًا للضبط يساوي `1` دون فرض حد أدنى `2`. عدد عمال Pi المقيمين يُحدد وفق القياس، لا بافتراض القدرة على تشغيل 6. لا تُنشئ خدمة Queue جديدة؛ إن لزم طابور محدود وفصل مهام خفيفة وثقيلة فداخل Pi Central الحالية مع عدالة بين المستخدمين وحالات `queued/running/cancelled/failed`.
- امنع إعادة تشغيل Prompt تلقائيًا بسبب timeout أو SSE reconnect أو فقد receipt، ولا تؤدِّ إعادة المحاولة إلى تنفيذ ثانٍ لأمر Tool كان قيد العمل.
- لا تجعل دورة مزامنة النماذج الدورية تعمل بالتوازي مع Build ثقيل بلا حاجة؛ استخدم آلية الصيانة الموجودة، وجدولة محافظة، وقفل/معاملة DB حتى لا ينفذها أكثر من عامل Gateway.
- راقب `RSS` لشجرة عمليات Pi + أبناء Bash/npm/node، وGateway وPostgreSQL وNginx، وCPU load، وswap/OOM، وtime-to-first-token ومدة build. لا تدعِ قيم RAM فعلية دون قياس TEST. استخدم قياسات قبل/أثناء/بعد مهمة Pi فعلية مع تقرير إجمالي لا يكشف أسرارًا.
- لا ترفع إعدادات PostgreSQL أو تعيد تشغيل DB عشوائيًا. راقب `shared_buffers` والاتصالات والذاكرة والإقفال والفهارس؛ أي ضبط لاحق يكون مبنيًا على قياس ويُراجع أثره على كل الخدمات.
- حدّد وقتًا أقصى للتنفيذ وحجم Queue وحدود عمليات فرعية/حجم استجابات؛ عند عدم السعة أعطِ خطأ صريحًا أو حالة انتظار دون إسقاط مشروع أو استهلاك كافة RAM.
- **سلامة متعددة العملاء:** تشغيل Pi وBash تحت نفس مستخدم OS ليس عزلاً آمنًا بمجرد فحص `directory` أو تخزين المفاتيح في DB. قبل السماح لعملاء متعددين بتنفيذ أدوات Shell غير موثوقة، يجب إثبات عزل العمليات/الملفات/الأسرار ضمن الإمكانات القائمة؛ وإلا تُسجّل `BLOCKED multi-tenant tools` ولا تُفتح هذه الصلاحية على الإنتاج. لا تُنشئ حاوية أو خدمة جديدة خلافًا للقيود.

**بوابة قبول موارد TEST:** بعد مهمة برمجية فعلية، لا يحدث OOM ولا انهيار PostgreSQL/Gateway ولا تختلط الجلسات؛ يثبت حد التزامن والانتظار والإلغاء؛ يعرض التقرير قياسات واقعية وأثر عدد العمليات، ولا يستنتج عدد مستخدمين مضمونًا من خاملة Pi.

### 13.4 الجداول القديمة والترحيلات — شرط لازم قبل إعلان DB جاهزة

- قال المالك إن الجداول السابقة قد مُسحت؛ يجب اعتماد إفادته مع **تثبيت حالة TEST الفعلية بدون عرض بيانات اعتماد**. تاريخ المصدر: `backend/alembic/versions/0017_user_provider_credentials.py` أنشأ `user_provider_credentials`، و`0036_native_only_provider_credentials.py` حاول إسقاط/تعطيل جداول الاعتماد القديمة. لا يجوز افتراض أنها ما زالت صالحة ولا إحياؤها داخل مخزن Pi المشترك.
- يريد المالك **حذف أي مفتاح في أي وقت**: النموذج الجديد يتطلب عملية حذف فعلية أو Revocation مع إبطال الاستعمال التالي فورًا، وتحديث كاش/جلسات Pi المرتبطة، وليس مجرد `DELETE` في UI أو تغيير علم `visible`.
